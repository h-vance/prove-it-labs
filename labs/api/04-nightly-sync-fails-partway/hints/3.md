Look at a rejected response in full:

```bash
for i in $(seq 1 8); do
  curl -s -o /dev/null -D - -H 'X-API-Key: wk_live_active_3c95' \
    "http://127.0.0.1:8101/v2/usage?page=$i" | head -1
done
```

Then inspect the headers on one that returns `429`:

```
Retry-After: 11
RateLimit-Limit: 5
RateLimit-Remaining: 0
```

`Retry-After` is the fix. The server has told you precisely how long to wait, so
the client should sleep for that long and retry the same page rather than
failing it or retrying immediately.

Edit `labs/api/_stack/request.sh` so that a `429` causes it to read
`Retry-After`, wait, and retry the page it was on. Capture headers with
`curl -D` to a file so you can read the value. Then run `tse check`.

Retrying immediately, or with a guessed delay, is the common wrong answer. It
turns one throttled client into a client that is throttled continuously.
